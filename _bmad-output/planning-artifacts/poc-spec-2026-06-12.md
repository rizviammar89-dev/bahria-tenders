# POC Specification — Bahria Town Home-Services Marketplace

## 1. What this is

A **proof-of-concept that doubles as Phase 0 demand validation**: real residents and real providers run the core loop on a real app. The full-MVP PRD remains the product vision; this document is the build target until the POC gate is decided. Decisions here were made explicitly by the founder (Ammar) on 2026-06-12 and should not be silently reopened.

**Platform pivot (supersedes architecture.md §Platform Selection):** built locally with code, not Bubble. The architecture doc's data-model integrity rules, naming/enum conventions, and localization locks still apply where in scope.

## 2. Proof statement, gate metrics, kill criterion

**Proof statement:** *Residents in 2–3 precincts will post real jobs through an app, and providers will bid on them, often enough to repeat.*

**Gate metrics (30 days live):**
| Metric | Target |
|---|---|
| Residents posting a job | 25+ |
| Jobs receiving ≥2 bids within 24h | 60%+ |
| Awarded jobs completed + rated | 50%+ |
| Repeat-post rate | ~20% |

**Kill criterion (accepted by founder):** after 6 weeks live, if **<15 jobs posted OR median bids-per-job <2** → stop and rethink. Not "iterate harder." Stop.

## 3. Stack (locked)

| Layer | Choice | Notes |
|---|---|---|
| Backend | **Supabase** (local via Docker for dev; hosted project for the live POC) | Postgres, RLS, Storage, Edge Functions, Studio |
| Mobile app | **Expo SDK 56 / React Native** (single role-switch binary: resident + provider) | Expo Go on a real budget Android during dev; EAS build for the POC APK |
| Admin | **Supabase Studio + SQL views + a runbook** | Refine deferred — one founder doesn't need a back-office framework |
| Push | **FCM via Expo Notifications** | Doorbell only — pull-based feed is the backbone |
| SMS | **Deferred post-POC** | See §6; dispatcher interface built now so adding SMS is one file |
| Crash reporting | **Sentry free tier** (week 3) | "You can't support what you can't see crash" |

Research basis: 18 verified GitHub repos — no high-star open-source project implements the post-job → bids → award → reputation loop; closest (Sharetribe Go) is deprecated with no bidding. Build on blocks, don't fork.

## 4. In scope

- Founder-provisioned **phone+PIN auth**: Supabase password auth against a synthetic email derived from the phone (`+923001234567@phone.bahria-tenders.local`). Login screen takes phone + PIN and derives the email client-side. Zero external dependencies.
- Core loop: **post job → broadcast (push) → providers bid one price → resident compares (stars + completed-job count) → award → contact exchange → mark complete → rate (write-once)**.
- Ratings permanence enforced in the database: insert-only `ratings` (no UPDATE/DELETE policy), RLS, pgTAP tests green **before any UI exists**.
- Push notification on new-matching-job (provider) and new-bid / awarded (resident) — only those.
- Pull-to-refresh provider job feed as the delivery backbone; founder WhatsApp fallback for missed jobs, logged.
- Urdu/English via two static string files (no i18n framework). Architecture localization locks apply: Western Arabic numerals, `Rs 1,500` format, icon + text, generous tap targets.
- Founder onboarding protocol: provision account, verify phone by personally calling, set `verified_by_admin`, walk the provider through disabling battery optimization (Xiaomi/Oppo/Vivo/Tecno/Infinix) in person.

## 5. Out of scope / deferred (with re-entry triggers)

## 6. Schema (7 tables) and integrity rules

Tables: `profiles` (role resident|provider, **phone TEXT UNIQUE NOT NULL, E.164 +92… with CHECK constraint**, `phone_verified_at TIMESTAMPTZ NULL` founder-set, precinct, `verified_by_admin BOOLEAN DEFAULT false`), `services` (~10 seeded categories), `jobs` (status enum `open → awarded → done → rated`, soft-cancel), `bids` (**UNIQUE(job_id, provider_id)**, single price, optional note), `ratings` (**insert-only, UNIQUE(job_id)**), `notification_log` (channel enum `push | whatsapp_manual | sms`, **idempotency_key UNIQUE**, sent/opened tracking), `disputes` (founder-only).

**Day-one must-be-right list (one-way doors — non-negotiable even in a POC):**
1. `profiles.phone` UNIQUE NOT NULL E.164 — the identity key regardless of auth mechanism. Post-POC migration to Supabase phone OTP = backfill `auth.users.phone` + flip provider; no table changes.
2. `phone_verified_at` nullable timestamp, founder-set via Studio (manual stand-in for OTP proof).
3. Ratings write-once: RLS denies UPDATE/DELETE; reputation aggregates written server-side only (`SECURITY DEFINER` functions / service role); zero INSERT/UPDATE grants on rating aggregates to `authenticated`.
4. Relational core with FKs — no denormalized POC shortcuts; jobs/bids/ratings as proper tables with locked enum slugs (architecture doc's enum table applies).
5. Notification dispatcher interface (`lib/notifications/`, `Channel` interface, `PushChannel` impl, templates keyed by event + locale) + `notification_log`. Adding Veevotech SMS later = `SmsChannel.ts` + one registry line.
6. pgTAP test suite (`supabase/tests/`) — one test per integrity rule, red before green, all green before any screen is built.
7. Image compression + retry on photo upload (2GB-RAM Android, bad networks).
8. Studio "unaccepted jobs older than X" view — the smoke detector for silently-dead push.
